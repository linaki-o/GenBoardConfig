版本：v0.1（草稿，待"比对逻辑"补充后定稿）
状态：需求待确认项见第 9 节

---

## 1. 背景与目标

### 1.1 背景

芯片 GPIO 的实际使用情况由硬件设计（原理图）与软件配置共同决定。硬件团队以 Excel 形式维护 GPIO 分配表（管脚名、GPIO 号、功能、对应配置项、期望值），而软件侧的板级配置以 `.c` 源文件形式维护。二者由不同人员、在不同时间维护，天然存在漂移：

- Excel 中新增/变更的 GPIO，`.c` 中未同步；
- `.c` 中的配置值与 Excel 期望值不一致（引脚号错、极性错、上下拉错）；
- 同一个 GPIO 在两处指向了不同的配置项或不同的芯片实例。

人工逐行比对数百行 GPIO 表效率低且易漏。

### 1.2 项目目标

构建一个 Windows 桌面工具：读取 GPIO 分配 Excel 与板级 `.c` 配置文件，借助大模型完成语义级核对，输出逐项差异结论，并在人工确认后将修正安全地写回 `.c` 文件。

核心价值：**把"人肉比对"变成"机器初审 + 人工确认"**，且 LLM 只负责理解与判断，写文件的动作必须由确定性代码完成。

### 1.3 成功判据

| 指标 | 目标 |
|---|---|
| 核对准确率 | 在给定样例集上，差异判定与人工结论一致率 ≥ 95% |
| 漏检率 | 人工发现的差异被工具检出的比例 ≥ 98%（漏检比误报更致命） |
| 效率提升 | 500 行 GPIO 表的核对耗时从 ~2 人日降至 ~1 小时（含复核） |
| 修改安全性 | 零语法破坏；每次修改均有可回滚备份与逐行 diff |
| 可审计 | 每次运行产出完整日志与报告，含 LLM 原始交互记录 |

## 2. 范围界定

### 2.1 纳入范围

- Excel（GPIO 分配表）读取、解析、列语义识别
- **档案驱动**（Profile）：按 Sheet 名自动选择比对档案，档案内定义「表结构 → 逐属性规则 → 修改落点」
- 板级 `.c` / `.h` 配置文件解析：宏定义、宏函数、结构体初始化、数组/映射表、**端口位表**（`BitsToByte`）、**条件编译多份定义**
- GPIO 实体归一化与跨表对齐（管脚名 / GPIO 号 / 芯片实例 / **原理图网络名**）
- 大模型语义核对与差异分类（**网络名 → 配置宏组** 的语义映射）
- 差异报告输出（差异清单 + 原始证据 + 逐属性结论）
- 修改草案生成、diff 预览、人工确认、写回与回滚（支持**位内改写**）
- 写回后的一致性/语法校验与逐属性复检
- 多模型供应商适配（云端 API）、API 密钥安全存储

### 2.2 排除范围（本期不做）

- 不修改 Excel（只读）
- 不做原理图/网表解析
- 不做编译与固件烧录
- 不做多人协同、版本管理（由 Git 承担）
- 不做板级配置的全自动生成（仅在现有配置上做增量修正）
- **不做**条件编译生效分支的自动判定（需接入编译命令行）

## 3. 角色与用例

| 角色 | 描述 | 核心用例 |
|---|---|---|
| 板级软件工程师（主要用户） | 维护 `.c` 板级配置 | 导入 → 核对 → 看差异 → 确认 → 应用修改 → 提交 Git |
| 硬件工程师 | 维护 GPIO Excel | 提供/更新 Excel，核对差异结论是否与硬件一致 |
| 配置基线负责人 | 审核变更 | 审查 diff 与报告，决定是否入库 |

主要用例：

1. **UC-01 一次核对**：选择 Excel + `.c` → 运行 → 得到逐项结论与差异报告。
2. **UC-02 差异审阅**：在 GUI 表格中按状态/管脚/芯片过滤，逐条查看"期望值 vs 现值 + 原文证据"。
3. **UC-03 应用修改**：勾选要应用的变更 → 预览 diff → 确认 → 写回 `.c`（自动备份）→ 校验。
4. **UC-04 失败回滚**：校验不通过或用户反悔 → 一键恢复备份。
5. **UC-05 规则维护**：维护引脚别名表、配置项映射表、LLM 提示词与模型参数。

## 4. 功能需求

### FR-01 Excel 导入与解析

- FR-01.1 支持 `.xlsx` / `.xlsm`，支持多 Sheet。
- FR-01.2 首行默认是表头；表头列语义不固定，采用 **确定性映射表 + LLM 语义识别** 双通道：
  - 确定性映射：用户可维护的列名→字段别名配置（如"管脚/Pin/Pad" → `pin_name`）。
  - LLM 识别：映射未命中时，由 LLM 对表头与前若干数据行做一次列语义标注，结果写入会话，用户可纠正并保存为映射规则。
- FR-01.3 支持多级表头（合并单元格）与表头前的标题行/说明行跳过。
- FR-01.4 按当前已知结构建模为逐行记录：`管脚名 | GPIO号 | 功能 | 配置项 | 期望值`，并预留扩展列（如 芯片实例、上下拉、极性、复用功能、BOM 备注、来源原理图页）。
- FR-01.5 解析失败须给出精确到单元格坐标的错误信息，不中断整表解析；错误行标红并计入报告。
- FR-01.6 空行、合计行、备注行自动识别并跳过（由规则 + LLM 兜底判定）。

### FR-02 `.c` 配置文件解析

- FR-02.1 解析目标为"配置项集合"，支持的载体至少包括：
  - 宏定义：`#define CONFIG_LED1_GPIO 47`
  - 带函数宏形式：`#define CONFIG_LED1_GPIO(x)`
  - 结构体字段初始化：`{ .gpio = 47, .flags = GPIO_ACTIVE_LOW }`
  - 数组/映射表：`{ "LED1", 47 }, { "KEY1", 12 }`
  - 简单的函数调用参数：`gpio_config(GPIO_PC13, LED1, ...)`
- FR-02.2 每个条目保留：原始文本、文件路径、起止行号、列偏移，供报告"原文证据"与精确落点使用。
- FR-02.3 解析器为**可插拔**（Parser Registry），后续扩展 `.h`、`.dts`、`.config` 只需新增解析器，不改上层。
- FR-02.4 采用"轻量词法 + 规则"而非完整 C 编译前端，保证在无 GCC 环境下可用；若本机存在 GCC，可选启用 `gcc -fsyntax-only` 做严格校验。

### FR-03 归一化与实体对齐

- FR-03.1 **管脚名归一化**：`GPIO_PC13` / `PC13` / `gpio pc 13` / `GPIOC13` → 统一键 `PC13`；同时保留芯片实例信息（如 `GPIOA` vs `GPIOB` 同号不同实例必须区分）。
- FR-03.2 **GPIO 号归一化**：十进制/十六进制 (`0x2F`)/前缀形式统一为整数，并处理"每个芯片独立编号"与"全局编号"两种口径（由配置声明）。
- FR-03.3 **配置项键归一化**：去除厂商前缀差异、大小写差异、`_`/`-` 差异。
- FR-03.4 产出 **候选匹配对**：先做确定性精确匹配（管脚名、GPIO 号、配置项键、功能名），再对未匹配项交给 LLM 做语义匹配。
- FR-03.5 **一对多/多对一**必须显式标记为歧义，交由 LLM 判定并由用户确认，不允许静默取其一。

### FR-04 大模型语义核对

- FR-04.1 采用 **两阶段 LLM**：
  - 阶段 A（表头/结构识别，仅在需要时调用）：输出列语义映射。
  - 阶段 B（逐条核对）：批量输入 Excel 记录 + 相关 `.c` 上下文切片，输出结构化 JSON 结论。
- FR-04.2 阶段 B 必须**分批**（建议 10–30 条/批），带预算控制与断点续跑（缓存已判定批次）。
- FR-04.3 输出必须是 **受 JSON Schema 约束的结构化结果**（见 6.2），字段不合法即判该批失败并重试，重试仍失败则标为 `unresolved` 交人工。
- FR-04.4 每条结论必须携带 **证据引用**（文件、行号、原文片段）；无证据的结论视为无效。
- FR-04.5 Prompt 中不得包含 API Key 等敏感信息；`.c` 文件中若存在疑似密钥/口令字段，按规则**自动脱敏**后再送模型（可配置）。
- FR-04.6 LLM 供应商抽象为 `LLMProvider` 接口，云端实现至少支持 OpenAI 兼容接口（覆盖多数国内网关）、Anthropic、通义等，通过配置文件切换，默认走 OpenAI 兼容协议。

### FR-05 差异判定规则

每条记录判定为以下状态之一，状态定义与判定优先级固定：

| 状态 | 含义 | 默认动作 |
|---|---|---|
| `match` | 期望与现状一致 | 无 |
| `missing` | Excel 期望存在，`.c` 中未找到对应配置 | 新增（需确认落点） |
| `mismatch` | 找到对应配置但值/极性/功能不一致 | 修正 |
| `ambiguous` | 存在多个候选或证据不足 | 人工确认 |
| `not_applicable` | 该 Excel 行不适用于当前 `.c`（如属于其他板型/芯片） | 无（需说明理由） |
| `unresolved` | LLM 调用失败/输出非法 | 人工确认 |

- FR-05.1 判定必须可追溯到规则或 LLM 结论，并携带置信度。
- FR-05.2 低置信度（阈值可配，默认 0.8）自动降级为 `ambiguous`，不自动生成修改。
- FR-05.3 用户可在 GUI 中手工改判任一条目，改判结果优先于 LLM 结论，并记录为"人工修订"。

### FR-06 变更草案与 diff 预览

- FR-06.1 变更以 **ChangePlan** 形式描述：`{类型, 目标定位, 原值, 新值, 依据}`，类型至少支持：`set_macro`、`set_struct_field`、`set_array_item`、`insert_block`、`none`。
- FR-06.2 生成**逐行 unified diff**并在 GUI 中并排/叠加展示，标出新增、修改、删除行。
- FR-06.3 明确列出**不可自动修改**的情况（无法定位落点、需新增函数/头文件、影响面超出单行），这些必须以"人工处理建议"呈现而不是硬改。

### FR-07 修改应用与安全机制

- FR-07.1 应用前自动备份原文件（带时间戳，同目录 `.bak` 或独立 `backup/` 目录）。
- FR-07.2 仅允许白名单编辑操作：修改宏右值、结构体字段值、数组元素值；**禁止**删除函数、修改函数签名、改变控制流。
- FR-07.3 修改严格基于**行/列偏移**，不依赖行号（行号在多次修改后会漂移），实现上采用"先算全部编辑、再一次性从后往前应用"的策略。
- FR-07.4 应用前二次确认；应用后立即执行校验（见 FR-08）。
- FR-07.5 校验失败 → 自动回滚到备份，并给出失败原因。
- FR-07.6 支持"仅导出修改后文件"而不覆盖原文件（供 Git PR 流程）。

### FR-08 校验

- FR-08.1 结构校验：括号/花括号配对、宏定义行完整性、数组元素逗号与分号完整、字符串字面量闭合。
- FR-08.2 语义校验：修改后重新解析，把 `.c` 的配置项集合与 Excel 期望重新比对，验证目标差异已消除且**未引入新差异**。
- FR-08.3 若本机有 GCC，额外执行 `gcc -fsyntax-only`（可选开关，默认关闭）。
- FR-08.4 校验结论分 `pass` / `warn` / `fail`，`fail` 阻止最终落盘。

### FR-09 报告输出

- FR-09.1 核对报告（HTML，附带可打印样式）：概览统计、状态分布、逐条明细（含证据、置信度、建议动作）。
- FR-09.2 修改报告：修改清单 + 完整 diff + 校验结论 + 备份路径。
- FR-09.3 报告可导出 HTML / CSV / Markdown；支持"仅导出差异项"。
- FR-09.4 报告中不得出现脱敏前的敏感内容。

### FR-10 配置与凭证

- FR-10.1 应用配置（模型、端点、批量大小、置信度阈值、是否脱敏、路径等）使用 YAML 配置文件 + GUI 设置页双写。
- FR-10.2 API Key 存放于 Windows **Credential Manager**（或 DPAPI 加密文件），**明文不落盘、不进日志、不进报告、不进 Git**。
- FR-10.3 配置变更写入本地 `config/settings.local.yaml`，并被 `.gitignore` 排除。

### FR-11 审计与日志

- FR-11.1 结构化日志（时间、级别、模块、会话 ID）。
- FR-11.2 记录：文件哈希、解析统计、每批 LLM 请求/响应摘要（脱敏）、人工改判记录、最终应用的操作清单。
- FR-11.3 每次会话生成独立日志文件与 `session.json` 摘要，便于复盘。

### FR-12 大模型供应商适配

- FR-12.1 `LLMProvider` 抽象接口：`complete(messages, schema, params) -> ParsedResult`。
- FR-12.2 实现：`OpenAICompatibleProvider`（OpenAI / 通义 / DeepSeek / 各类网关）、`AnthropicProvider`；预留 `LocalProvider`。
- FR-12.3 统一的重试（指数退避）、超时、限流处理、token 预算统计与成本估算展示。
- FR-12.4 Prompt 模板外置为文件，支持版本管理与热更新。

### FR-13 档案（Profile）驱动

- FR-13.1 档案以 YAML 外置（`config/profiles/*.yaml`），包含：目标 Sheet、列语义映射、**待核对属性清单**、期望值归一映射、C 侧宏组/位表规则。
- FR-13.2 打开 Excel 时按 **Sheet 名**自动选择档案（其次按表头关键字打分），界面显示当前档案。
- FR-13.3 档案未命中时回退到通用模式（一行一配置项），两条链路共用同一套基础设施与 GUI。
- FR-13.4 新增板型只需新增 YAML，不改代码。

### FR-14 逐属性核对（档案模式）

- FR-14.1 一行 Excel 可展开为**多个待核对属性**（引脚 / 方向 / 输出类型 / 上电电平 / …），每个属性独立给出结论与证据。
- FR-14.2 行状态 = 可核对属性中最严重的状态（不一致 > 缺失 > 歧义 > 未解析 > 不适用 > 一致）；不可核对属性不影响行状态。
- FR-14.3 属性来源可以是配置文件的多种形态：宏组（`_PORT`/`_BIT`/`_ACTIVE`）、**端口位表**（`BitsToByte` 逐位）、功能块常量（PWM/PSM 恒为输出、恒为推挽）。
- FR-14.4 无法在配置中编码的属性（如省电/关机电平）必须显式标为「不可自动核对」，不得静默忽略。
- FR-14.5 同一宏存在多份**条件编译**定义时，全部保留并在结论与依据中标注条件上下文，置信度下调。

### FR-15 网络名 → 配置宏组映射

- FR-15.1 确定性优先：① 宏定义行尾注释命中原理图网络名；② 宏组名称 token 相似 + **Excel 引脚一致**消歧。
- FR-15.2 上述方法无法唯一确定时，交大模型在候选列表中语义选择，输出宏组名 + 置信度 + 理由。
- FR-15.3 模型映射置信度低于阈值（默认 0.75）时，行状态降级为「歧义」，**不生成修改**。
- FR-15.4 映射结果须随核对结果一并保存，写回后的复检必须使用同一映射，否则会产生假阳性差异。

### FR-16 位内改写与引脚独占性

- FR-16.1 支持改写端口位表中**单个位**（只替换该实参，不动其它位与排版），落点精确到列区间。
- FR-16.2 同一 (端口, 位) 被多个信号组引用时，**禁止自动改写**，只输出人工处理建议。
- FR-16.3 配置项缺失时不自动新增宏组，只给出「建议新增宏组」的人工建议。

## 5. 非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| NFR-01 | 平台 | Windows 10/11 x64，无需管理员权限运行 |
| NFR-02 | 性能 | 500 行 GPIO 表解析 < 5s；核对总耗时（100 次云端调用）< 10min；GUI 响应不冻结（后台线程 + 进度反馈 + 可取消） |

| NFR-05 | 安全 | 见 FR-10、FR-04.5；上传到云端的内容须可预检（"将要发送的内容"预览开关） |
| NFR-06 | 可用性 | 中文界面；新手可按"三步向导"完成首次核对；错误提示给出可执行的下一步 |
| NFR-07 | 可测试性 | 领域层与解析层纯函数化，提供脱网单测样本；LLM 层可 Mock |
| NFR-08 | 可维护性 | 解析器、比对规则、Prompt、列映射均为外部可配置，升级不改业务代码 |
| NFR-09 | 兼容性 | `.c` 文件为 UTF-8 / GBK 混合时须正确识别；CRLF/LF 换行不被破坏 |
| NFR-10 | 可复现 | 同一输入 + 同一模型版本 + 同一 prompt 模板，应得到一致的判定结论（提示词需含版本号与判定规则描述） |

## 6. 核心数据模型（概要）

### 6.1 领域对象

```
GPIORequirement        # Excel 一行归一化后的需求项
  ├ id, pin_name_raw, pin_key(GPIOx,pin)
  ├ gpio_num, gpio_scope(per_chip/global)
  ├ function_name, config_key, expected_value
  ├ extras{ polarity, pull, mux, chip_instance, sheet, row_no }
  └ parse_status(ok/ambiguous/error)

ConfigEntry            # .c 中解析出的一个配置项
  ├ kind(macro/struct_field/array_item/call_arg)
  ├ key, value_raw, value_normalized
  ├ file, start_line, start_col, end_line, end_col, raw_text
  └ owner_context(所属结构体/数组/宏分组)

MatchResult            # 一条需求的核对结论
  ├ requirement_id, status, confidence
  ├ matched_entry_ids[]
  ├ current_value, expected_value
  ├ evidence[]{ file, line, snippet }
  ├ proposed_change{ type, target, old, new, reason }
  ├ source(deterministic/llm/human)
  └ notes
```

### 6.2 LLM 结构化输出契约（阶段 B）

```jsonc
{
  "items": [
```

## 8. 异常与边界场景

| 编号 | 场景 | 期望行为 |
|---|---|---|
| E-01 | Excel 表头多级合并/有前置说明行 | 自动定位表头；失败时提示并允许手工指定表头行 |
| E-02 | Excel 中同一管脚多行（多复用功能） | 不去重，全部参与核对；冲突项标 `ambiguous` |
| E-03 | `.c` 中配置项存在多份（多处 `#define` 同名） | 全部列出，标 `ambiguous`，由用户选择落点 |
| E-04 | `.c` 使用宏拼接/间接引用（值是另一个宏名） | 记录为 `value_kind=symbolic`，核对时按符号解析，解析不了则 `ambiguous` |
| E-05 | Excel 期望值格式多样（`47` / `GPIOA_5` / `GPIO_ACTIVE_LOW` / 文本描述） | 归一化失败则交 LLM 判定，仍不确定标 `ambiguous` |
| E-06 | 芯片实例不一致（Excel 的 GPIOA 与 `.c` 的 GPIOB） | 明确标为不匹配，禁止"数字相同即匹配" |
| E-07 | 云端 API 超时/限流/鉴权失败 | 指数退避重试；最终失败则该批标 `unresolved`，其余批次继续 |
| E-08 | LLM 返回非法 JSON | Schema 校验失败 → 重试 1 次 → 标 `unresolved`，记录原始响应 |
| E-09 | `.c` 文件为 GBK 编码 / CRLF 换行 | 正确解码，写回时保持原编码与换行风格 |
| E-10 | 用户在核对过程中再次编辑源文件 | 记录文件哈希；写回前比对哈希，不一致则中止并要求重新核对 |
| E-11 | `.c` 超过 5000 行 | 分块索引 + 按需切片送模型，避免整文件进上下文 |
| E-12 | 多个 Excel Sheet 对应不同板型 | 允许选择目标 Sheet；其余 Sheet 标 `not_applicable` |

## 11. 术语表

| 术语 | 含义 |
|---|---|
| GPIO 分配表 | 硬件侧维护的 Excel 表，逐行描述一个 GPIO 的用途与期望配置 |
| 板级配置 | 软件侧的 `.c` 文件，承载 GPIO 的实际配置项 |
| 归一化 | 把管脚名/GPIO 号/配置键统一到可比较的规范形式 |
| 匹配对 | 一条 Excel 需求与一个 `.c` 配置项之间的候选关联 |
| ChangePlan | 结构化的修改计划，尚未落盘 |
| 落点 | `.c` 文件中某个待修改文本的确切位置（行 + 列区间） |
| 证据 | 支撑某一判定结论的 `.c` 原文片段与位置 |
